Find Anything

Permission-aware exact search over the Google Drive files you choose. Every answer cites the page, slide or cell it came from, and every search leaves an auditable receipt of what was found, missed or off-limits.

Live public betaCode

  • TypeScript
  • Cloudflare Workers + D1
  • SQLite FTS5
  • OAuth 2.0 + PKCE
  • AES-GCM
  • MCP

Problem

When people or AI agents search company documents, they can't tell what was searched, what was skipped, or whether a file was off-limits. Two versions of a pricing sheet disagree and the search quietly picks one.

Approach

  1. Connect. Google OAuth with PKCE and the narrow drive.file scope, so the app sees only files the user picks. Refresh tokens are encrypted at rest with AES-GCM, a key id and associated data that binds each ciphertext to its row.
  2. Index. Background jobs turn Docs, Slides, Sheets and PDFs into units that remember their exact location. Jobs run in short hops under Workers' limits, with compare-and-swap state transitions and leases so a crashed or duplicated hop can't corrupt progress.
  3. Search. Every query re-checks Drive permissions and refuses if it can't confirm them. A SQLite FTS5 index in D1 proposes candidates; exact whole-word rules decide matches; conflicting sources are both shown.
  4. Prove it. Each search writes a trace and a receipt with coverage: which files were searched, which failed, which were excluded.

Key decisions

  • No permission cache. A revoked file must disappear on the next search, so correctness beats the cost of one ID-only Drive call per query.
  • Workers and D1. One deployable unit with low cost, in exchange for tight limits on outbound calls and query parameters, which the job design works around.
  • The index proposes, the rules decide. FTS5 makes search fast, but a test checks it returns exactly what the full scan returned.

Results

A rare-phrase search over 100,000 indexed units dropped from 286 ms to 30 ms after moving matching into FTS5 (in-process SQLite on an M2 Pro); a word found in almost every file went from 580 ms to 329 ms. 264 tests run in CI, including repository tests on in-memory SQLite with every migration applied. The app is live in public beta; Google's brand verification is pending.

What a review found, and what changed

Search loaded every document into memory per query; "exact" matching was substring matching ("cat" matched "category"); the coverage report counted failed files as zero; one transient Google error disabled search until a manual resync; the audit trail recorded every file as "allowed" regardless; and the admin token comparison wasn't constant-time. All fixed, with behavioral tests.

Next

Move the remaining whole-corpus routes (conflicts, citations) onto the index, upgrade the web framework past its open advisories, and get an external security review.

AIR: Airspace Incident Record

Turns a crashed drone's PX4 flight log into rule-based findings and a signed, tamper-evident record that a third party can verify offline.

Code

  • Python
  • Ed25519
  • Merkle trees (RFC 9162)
  • RFC 3161
  • PX4 ULog

Problem

After a drone incident, an operator has a log file and a pilot's memory. Insurers and investigators need to know what happened, whether the operator followed its own procedures, and that the write-up wasn't edited afterwards.

Approach

  1. Parse the log into time series and events (arming, mode changes, altitude, GPS, battery, vibration).
  2. Run deterministic rules. Every finding cites its threshold and where that threshold comes from.
  3. Check the operator's own procedure file, such as a 120 m ceiling, with a stated measurement tolerance.
  4. Hash the report, its HTML rendering and the source log into a Merkle tree, sign the root with Ed25519, and optionally timestamp it with an RFC 3161 authority.
  5. Ship a single-file verifier that checks everything offline against a key fingerprint published out of band.

Key decisions

  • Rules, not a learned model. Every finding has to survive cross-examination line by line. The cost is recall.
  • Abstain instead of guess. NOT_EVALUABLE and MARGINAL are first-class verdicts; barometric altitude is never passed off as height above ground.
  • Trust comes from outside the bundle. A signature only proves someone signed, so the verifier needs an independently published fingerprint and says plainly when it doesn't have one.

Results

On 66 labelled public logs, the "log ends in flight" signal had 4 true positives, 0 false positives and 12% recall. It is an evidence tool, not a crash detector. The test suite has 84 tests, including forged-bundle, wrong-key and mismatched-timestamp cases.

What a review found, and what changed

An independent review showed the verifier trusted whatever key was inside the bundle, the timestamp check compared two locally computed values, two analyzers never fired on real logs because PX4 stores those fields as arrays, and the HTML report sat outside the signature. All four are fixed and covered by tests.

Next

Impact-signature detection, ArduPilot logs, a fresh evaluation on new data, and signing keys held in hardware with a published identity.

OSDR plain-English search

Ask NASA's Open Science Data Repository a question in plain English and get the matching space-biology datasets and their sample rows.

CodeData: NASA OSDR

  • Python
  • FastAPI
  • BM25
  • Embeddings (bge-small)
  • Reciprocal rank fusion
  • Claude structured output

Problem

OSDR holds 641 datasets and 51,369 samples. Finding the right ones normally means knowing its metadata schema: organism, material, assay, mission.

Approach

Each dataset becomes one paragraph of text, searched two ways: BM25 for exact terms and bge-small embeddings for meaning. Reciprocal rank fusion merges the two lists by rank, so their different score scales never need calibrating. An optional Claude step proposes filters, and every proposed value is checked against the real vocabulary before it can affect ranking. Near-duplicate datasets collapse into one result.

Key decisions

  • Hybrid retrieval. Embeddings missed the exact code "RR-6"; keywords miss synonyms like "droppings" for "feces".
  • The model can propose, not invent. Invalid filter values are dropped and shown as dropped, and the original question is always ranked.
  • Sparse fields don't count against a dataset. Mission is missing for half the corpus, so absence isn't evidence.

My original evaluation reported 48/50 in the top 5. A review showed plain BM25 tied it, because the test questions paraphrased dataset titles. Again

An offline-first web app that ranks a household's dinners with quick "this one or that one?" matchups, then suggests what to cook tonight and why.

CodeLive app

  • JavaScript
  • PWA / service worker
  • localStorage
  • node:test

Approach

After cooking, you answer "would you make it again?" A new meal is placed by binary insertion: compare it with the middle meal, keep the half it belongs in, repeat. Everything lives in the browser, and a versioned service worker makes it installable and usable offline.

Key decisions

  • Pairwise matchups instead of stars. People compare more consistently than they score.
  • No backend. Private and offline by default; the trade-off is no sync between devices.

Results

Worst case is ceil(log2(n + 1)) matchups, checked by simulation for every list size up to 128. Measured averages: 3.5 matchups for 10 meals, 6.7 for 100. 39 tests cover ranking, suggestions and saved-data repair.

What a review found, and what changed

A stored XSS bug through recipe links, saves that could be silently wiped, placement that stopped after one comparison, suggestions that ignored the ranking, and a service worker that could mix old and new files. All fixed, with tests.

How I build

I build with AI coding assistants, mainly Claude Code and OpenAI Codex, and every repository says so. I choose the problem and the design, and I hold the work to evidence: tests in CI, evaluations with stated limits, and independent code reviews.

In October 2026 I had each main project reviewed by a fresh set of eyes looking for real defects. The reviews found a forgeable verifier, an evaluation that a simple baseline tied, a coverage report that hid failed files, and a stored XSS bug. Those findings, and the fixes, are written up in each case study above, because knowing where your own work is weak matters more than claiming it isn't.
